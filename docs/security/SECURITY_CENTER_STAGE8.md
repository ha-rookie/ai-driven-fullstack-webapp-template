# Stage8 #420 — Security Center, read-only vertical slices

## Slice E: real CI control-step evidence, only on demand

A Workflow run conclusion is not proof that any particular security check step ran. Administrators now may explicitly inspect the **latest completed run** for one of the four fixed sources through a second, narrowly scoped form of the existing authenticated `GET /api/admin/security/center` endpoint. The request adds `sourceId` but **never accepts a client-selected Run ID, URL, job name, step name, SHA or additional query key**. The server authenticates and enforces `administration:manage` for `workhub-company` *before* the source reader or public GitHub API can run. It then selects the source's latest successfully authenticated public Workflow metadata already provided by the existing source reader; only after confirming a completed run does it retrieve its jobs (one GET for one selected run). The fixed allowlisted workflow-specific job and check step are defined in server-owned policy, not supplied by the requester.

Only the expected run ID, commit SHA, job name and exact step name are trusted. The projected result includes the source ID, Run ID, commit SHA, one fixed step identifier and the normalized **CI step outcome** (success/failure/skipped/etc.). Unknown, duplicate, inconsistent, missing, oversized, redirected or inaccessible job responses fail closed to `unavailable`; pending or absent latest runs remain `not-run`. Provider free-form text, job URLs, arbitrary step names, actor data, logs, artifacts and exception details are never returned. A bounded 15-second request and 256 KiB streaming limit protect the Worker; one per-isolate 5-minute success/failure cache per source limits public API quota exposure. This is still not durable or cross-isolate quota enforcement.

The UI displays the real step result only after user interaction, validates the exact source ID, current latest Run ID, SHA and fixed step code, and warns when a result cannot be observed. A run changing between display and detail read requires refreshing instead of presenting an unrelated step as evidence. A step success proves only that *this precise Actions step completed with success on this SHA*; it is **not** a verified Security Finding list, a scan result content audit, evidence freshness for #488, present Production code or SCS certification. The global Security Center remains Gray/not-assessed and its Finding count stays `null`. Browser tests use explicitly synthetic provider fixtures and never claim a live Production scan. Formal ST #694 remains Not Run.

The seven planned paths are this design, `src/worker/administration/security-center-source-reader.ts`, `src/worker/administration/security-center-api.ts`, `src/reference/admin/SecurityCenter.tsx`, `tests/security-center-source-reader.test.ts`, `tests/security-center-api.test.ts`, and `e2e/tests/workhub-security-center.spec.ts`. No workflow, secret, resource, migration, D1, deployment or global roadmap change. #420 remains Open, original 2/11 checked; a verified Finding feed and requirement-to-validated-evidence trace remain outstanding.

## Slice D: actionable CI status triage (independent of verified Finding evidence)

After Slice B connected real GitHub workflow execution metadata, the Security Center should let administrators tell which **CI source** needs their attention, rather than reading four raw run histories one by one. This slice adds a pure, fail-closed classification for the existing fixed four CI sources: unavailable/not-connected/not-run/running/failure-or-cancelled/skipped/last-run-success, plus a UI filter to show only sources with an incomplete or actionable CI state. **Successful CI execution is never a Security Finding assessment, current Evidence, current main or Production equivalence.** No Green security posture is derived; Finding/source coverage and lastSuccessfulCheckAt remain independent and unknown until verified Finding evidence is connected.

A prior successful CI run is separately labelled **historical** when the latest execution is different. Its recorded SHA is compared explicitly with the latest execution's SHA; different SHA means the historical run cannot attest to the latest code. Success is scoped to the five fetched runs per workflow, never the full GitHub execution history. A latest-success assertion inconsistent with the last-success record fails closed instead of producing false reassuring text. Unknown/invalid CI DTOs are rejected at the existing UI boundary. The filter is client-side and affects only CI rows, not the global Security posture or SCS references.

The exact change scope is five paths: this design, `src/shared/security/security-ci-triage.ts` and `tests/security-ci-triage.test.ts`, existing `src/reference/admin/SecurityCenter.tsx`, and `e2e/tests/workhub-security-center.spec.ts`. No additional GitHub API calls, scanner, worker endpoint, credential, workflow, database or resource. Browser tests use explicitly synthetic post-auth fixtures; no formal ST #694 or Preview/Production checks are inferred. Original Issue #420 acceptance remains Open 2/11 until evidence-by-condition validation; this is **CI source health**, not the verified Finding source's last successful check or #488 Evidence freshness.

## Slice B: observe existing CI execution without inventing Finding evidence

After the separately approved #732 merge, the next incremental change connects the existing four public GitHub Actions workflows through a server-owned, GET-only reader. The existing endpoint authenticates and independently authorizes the fixed WORKHUB scope **before** invoking that reader. The repository and workflow filenames are allowlisted in code; request parameters, Cookies and credentials cannot choose a target or enter an outbound request. No workflow, scanner, token, binding, database, or remote resource is added.

The reader requests at most five runs per workflow. It validates repository/path identity, positive run IDs, exact SHA, controlled execution states and timestamp chronology, then reuses #727's source snapshot normalizer. Raw provider records, actor names, logs, artifacts and arbitrary URLs are discarded. The UI constructs run links only from the fixed repository and validated numeric run ID. It displays the observed run's SHA and event: these may be PR code and **are not the deployed application or current main**.

CI execution and Finding evidence remain separate axes. A successful workflow has `checkedFindingCount: null` and `freshness: unknown`. A failed or inaccessible source cannot become Green. `latestSuccessfulRun.updatedAt` means the update timestamp of a successful run **within the fetched five-run window**, not its exact job completion time, the all-history last success, a successful Finding assessment, or an SCS evidence freshness date. The previous success may reference a different SHA and is displayed separately from the latest state. If no success is found in that bounded window, the UI says so rather than claiming no check has ever succeeded.

Each GET rejects redirects, has a fifteen-second timeout (matching the existing runtime-evidence collector budget) and a 256 KiB streaming body limit, and uses no authentication header. Independent source failures produce `unavailable` only for that source. A per-isolate single-flight cache holds both successful metadata and failure results for at most five minutes, limiting retries to four GETs per five minutes per isolate; the original fetch time remains visible. Refresh failure discards previous success rather than representing it as current. This is a quota-saving cache, not a durable source of truth or a cross-isolate rate limiter. Public GitHub rate limits can still make reads unavailable. Local/Test never automatically calls GitHub; synthetic unit/browser fixtures are explicitly test-only.

Validation covers the GET allowlist and credential boundary, malformed/oversize/redirect/timeout failures, partial availability, success versus unknown Finding count, bounded historical success, cache expiry and authorization-before-read. Browser acceptance covers execution/failure/history metadata and unsafe API responses. A one-off live public API read is separate integration evidence; CI/browser fixtures are not Production scans. Original #420 acceptance remains 2/11 on main until an approved merge and evidence-by-condition review. Verified Findings, actual Finding freshness, SCS trace, remediation and formal ST #694 remain incomplete.

Provider contract: [GitHub REST workflow runs](https://docs.github.com/en/rest/actions/workflow-runs#list-workflow-runs-for-a-workflow). GitHub's `updated_at` is deliberately not renamed to a completed-check timestamp.

- The existing #724 `normalizeSecuritySourceCoverage` projects four presently unconnected sources into `not-checked`, `unmonitored`, `unknown`, with `checkedFindingCount: null` and without a successful-scan timestamp. - The Security Finding feed is **not connected**: `findings.items` and `findings.verifiedCount` are `null`. An unknown count is never reported as `0`; a successful CI run and Audit Event are not converted to Security Findings.

Its 43 requirements and static Responsibility/Control/Test/Evidence *references* are projected after authorization. The existing mapping's `source.verifiedAt` is **reference-source verification metadata**, not evidence freshness, a current scan, individual requirement compliance, or ★3/★4 SCS certification. Each requirement's evidence freshness is `unknown`; its Finding/Remediation bindings are `null`.
- The UI shows Gray/unassessed/unknown, source health and missing last-success information, plus bounded SCS requirement search. It handles denied/unavailable responses separately and offers a retry. The existing Audit Event viewer remains an independent navigation target; there is no invented Finding-to-Audit correlation.
